## Current Default Flow

The project now uses Polymarket resolved BTC 5-minute UP/DOWN outcomes as the default training target. BTC OHLCV direction remains useful for diagnostics, but it is not the default acceptance label.

```text
Binance BTCUSDT 1m OHLCV
    -> normalized Parquet
    -> shared feature builder on 5-minute grid rows
    -> resolved Polymarket label join
    -> training frame
    -> split train/validation acceptance
    -> full-train deploy artifact
    -> execution_engine/deploy/baseline
```

## Feature Build

Feature construction is centralized in:

```text
src/features/builder.py
src/features/registry.py
src/data/dataset_builder.py
```

The execution layer must not recompute BTC features independently. Offline and online paths must use the same registered feature builder and the feature list recorded in `artifact_manifest.json`.

Current constants:

```yaml
CORE_FEATURE_VERSION: v8
CORE_LABEL_VERSION: v1
```

Current production artifact feature count:

```yaml
feature_count: 1016
second_level_enabled: false
derivatives_enabled: false
```

Important leakage controls:

- Spot features use lagged/completed information only.
- Derivatives, when enabled, must be aligned with backward as-of joins only.
- Target, future, return-target, and label-derived columns must never be feature columns.
- Offline training, validation, inference, and signal generation must use the same feature schema.

## Full-Train Deploy Step

After a split artifact is accepted, the second step retrains on all split rows and writes the deploy artifact.

```powershell
rtk python scripts/model/train_online_full_train.py `
  --cached-split-dir artifacts/data_v2/experiments/20260520_polymarket_resolved_extended_history_baseline `
  --accepted-artifact-dir artifacts/data_v2/experiments/20260520_polymarket_resolved_extended_history_baseline `
  --output-dir execution_engine/deploy/baseline `
  --config experiments/configs/20260520_polymarket_resolved_extended_history_baseline.yaml `
  --horizon 5m
```

Rules:

- Use the exact same config hash as the accepted artifact unless `--allow-config-mismatch` is intentionally used and documented.
- Thresholds come from the accepted offline validation artifact.
- The deploy manifest must contain `offline_validation_metrics`.
- `full_train_metrics` are diagnostics only and are not valid acceptance scores.
- The deploy directory is tracked by git even though general `artifacts/` outputs are ignored.


## Quick Rebuild Checklist

1. Update or verify Binance normalized 1-minute klines.
2. Update or verify `artifacts/data_v2/labels/polymarket_resolved/btc_updown_5m.parquet`.
3. Build the training frame with `scripts/data/step4_features/build_dataset.py`.
4. Create or reuse a chronological cached split.
5. Run `scripts/model/train_model.py` and accept only if validation `coverage >= 0.70`.
6. Compare validation `selection_score`, `utility`, `accepted_sample_accuracy`, signal counts, and coverage against the previous accepted baseline.
7. Run `scripts/model/train_online_full_train.py` using the accepted artifact as threshold source.
8. Verify execution can load `execution_engine/deploy/baseline/artifact_manifest.json`.
9. Run relevant tests and commit the reproducible config, code, docs, and deploy artifact.
